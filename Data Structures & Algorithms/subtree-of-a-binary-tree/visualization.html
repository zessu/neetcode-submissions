Subtree of Another Tree

LeetCode 572 — Does subRoot appear as an exact subtree of root?

Tree DFS Binary Tree String Matching

Problem Overview

A subtree of root is a node together with all of its descendants. We must decide whether some node in root roots a tree that is identical to subRoot — same values and same shape, including every missing child.

Input: root = [3,4,5,1,2], subRoot = [4,1,2] Output: true (the subtree rooted at 4 matches exactly) Input: root = [3,4,5,1,2,null,null,null,null,0], subRoot = [4,1,2] Output: false (the matching node 4 now has an extra descendant 0)

The subtle part is that a subtree cannot be "part of" a larger branch: if the candidate node has an extra child, the comparison fails.

Approach 1: DFS at Every Candidate Node (Implemented)

Intuition: Every node of root is a candidate subtree root. Walk all of them; whenever the value matches subRoot.val, compare both trees node-for-node.

Time: O(n · m) Space: O(hroot + hsub)
Example 1 — candidate nodes and the successful comparison

root = [3,4,5,1,2]

subRoot = [4,1,2]

compareTrees(3, 4) → 3 ≠ 4, reject candidate
compareTrees(4, 4) → 4 = 4, then 1 = 1, then 2 = 2 → true
compareTrees(5, 4) → 5 ≠ 4

  1. Traverse every node of root (preorder in the implementation).
  2. At each node, if node.val === subRoot.val, call compareTrees.
  3. compareTrees: both null → true; both non-null with equal values → recurse on both child pairs; anything else → false.
  4. Remember a success in a flag and keep traversing. Return the flag.

Approach 2: BFS at Every Node

Intuition: The candidate search can be level-by-level. A queue visits every node; the same compareTrees helper checks matches.

Time: O(n · m) Space: O(w + hsub)
BFS order on root = [3,4,5,1,2]
level 0 3 3 ≠ 4
level 1 4 compare → true 5 5 ≠ 4
level 2 1 2 queued, then visited

BFS checks shallow candidates first, which can find a match sooner, but the worst-case bound is unchanged.

Approach 3: Serialize + Substring Search

Intuition: Preorder with explicit # null markers gives every tree a unique string. Then "is a subtree" becomes "is a substring".

Time: O(n + m) with KMP Space: O(n + m)
Example 1 serialization (tokens separated by commas)
root = ,3,4,1,#,#,2,#,#,5,#,#, subRoot = ,4,1,#,#,2,#,#, ,4,1,#,#,2,#,#, root: ,3,4,1,#,#,2,#,#,5,#,#, ^^^^^^^^^^^^^ substring found → true
Example 2 serialization
root = ,3,4,1,#,#,2,0,#,#,#,5,#,#, subRoot = ,4,1,#,#,2,#,#, root: ,3,4,1,#,#,2,0,#,#,#,5,#,#, ^ the extra 0 changes the encoding → no match → false

The leading comma prevents a match from starting inside a multi-digit value (e.g. 12 inside 512). KMP keeps the search linear; a naive includes can degrade to O(n · m).

Approach 4: Subtree Hashing (Merkle-Style)

Intuition: Compute a hash for every subtree bottom-up. Identical trees produce identical hashes, so matching the hash of subRoot against the hashes of all subtrees of root answers the question.

Time: O(n + m) expected Space: O(n + m)
Bottom-up hashes for root = [3,4,5,1,2]
hash(4) = mix(4, hash(1), hash(2)) = same as hash(subRoot) → true

Hash values above are illustrative. A real implementation mixes values with multiplication/xor, not addition, and should verify a hash hit because collisions are possible.

Approach Comparison

Approach Time Space Pros Cons
DFS at every node (implemented) O(n · m) O(hroot + hsub) Direct definition; short; no auxiliary structures Repeats comparisons when values duplicate
BFS at every node O(n · m) O(w + hsub) Iterative; shallow matches found early Queue can grow to O(n); same repeated work
Serialize + KMP O(n + m) O(n + m) Optimal; tree equality becomes string search Delimiter details; extra memory; KMP needed for the bound
Subtree hashing O(n + m) expected O(n + m) Fast; hashes reusable across many queries Collision risk; needs careful mixing/verification

Key Insights & Common Pitfalls

The one-sentence rule: a subtree must match the candidate node's entire descendant structure. Extra children break the match, even if all the values in subRoot are present.
  • Null positions matter. compareTrees must return false when exactly one side is null. Comparing values without shape accepts "substructures" that are not subtrees.
  • One failed candidate is not the answer. Duplicate values mean several nodes can be candidates; keep searching after a mismatch.
  • The value filter is necessary for speed. Without checking root.val === subRoot.val first, the comparison runs at every node and the constant factor grows.
  • Early exit is optional here. The submission stores success in isSubTree and keeps traversing; returning immediately would be faster but does not change correctness.
  • subRoot is non-empty by constraint. The code reads subRoot.val directly. A defensive version would handle subRoot === null first.
