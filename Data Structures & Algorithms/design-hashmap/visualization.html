Design HashMap

LeetCode 706 — Build put / get / remove without built-in hash tables

Hash Table Design Array Linked List Hash Function

Problem Overview

Implement a map supporting put(key, value), get(key) (return -1 if absent), and remove(key). Keys and values are integers in [0, 10^6], and at most 10^4 operations are performed. The follow-up asks for an implementation with no built-in hash table.

Input: ["MyHashMap","put","put","get","get","put","get","remove","get"] [[], [1,1], [2,2], [1], [3], [2,1], [2], [2], [2]] Output: [null, null, null, 1, -1, null, 1, null, -1]

The sequence checks insertion, a miss, an update of an existing key, and deletion. An update must not create a duplicate entry.

Approach 1: Parallel Arrays / Linear Scan

Intuition: Store keys and values in two parallel arrays and scan for the key on every operation. No hashing, no collisions — just slow membership tests.

Index 2 was written twice: the first put(2, 2) stored 2, then put(2, 1) overwrote it with 1. -1 marks an empty slot, which is why negative values cannot be stored with this sentinel.

Intuition: Hash the key into a small bucket array and let colliding keys share a linked list. The bucket index narrows the search; the chain resolves collisions.

Approach 4: JavaScript Object (Implemented)

Intuition: A plain object already is a hash table managed by the engine. Numeric keys are coerced to strings, hashed internally, and stored; we only need to expose the three operations.

Membership is tested with key in values, not truthiness, so a stored value of 0 is still returned as 0. remove uses delete; assigning undefined would leave the property present.

class MyHashMap { values: Record<string, number> = {}; put(key: number, value: number): void { this.values[key] = value; } get(key: number): number { return key in this.values ? this.values[key] : -1; } remove(key: number): void { if (key in this.values) { delete this.values[key]; } } }

The worst case for chaining and for the object is O(n) when all keys collide. Direct addressing has no collisions, but its memory is fixed regardless of how many keys are actually used.

Common Pitfalls

  • Truthiness instead of membership: if (values[key]) treats a stored 0 as missing. Use key in values / Object.hasOwn.
  • in walks the prototype chain: "toString" in {} is true. Integer keys dodge this, but a general map should use a null-prototype object or Object.hasOwn.
  • Assigning undefined instead of deleting: the key still exists, so get returns undefined rather than -1.
  • Appending on update: put on an existing key must overwrite, never create a duplicate entry.
  • Key 0: a valid key that is falsy; never use it as a "missing" signal.
