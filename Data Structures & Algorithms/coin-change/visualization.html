Coin Change

LeetCode 322 — fewest coins to reach an amount, with unlimited coins

Dynamic Programming Memoization BFS Array

Problem Overview

Given unlimited coins of the listed denominations, return the minimum number of coins that sum to amount, or -1 if it is impossible. amount = 0 needs zero coins.

Input: coins = [1, 2, 5], amount = 11 Output: 3 (11 = 5 + 5 + 1) Input: coins = [2], amount = 3 Output: -1 (every reachable sum is even) Input: coins = [1], amount = 0 Output: 0

Greedy fails in general: for coins = [1, 3, 4] and amount = 6, taking 4 first gives 3 coins, while 3 + 3 uses only 2.

Approach 1: Brute-Force Recursion

Intuition: Try every coin at every step and recurse on the remaining amount. The answer is one plus the best answer for the remainder.

Time: exponential Space: O(amount / min coin) stack
Call tree for amount 6 with coins [1, 2, 5] — duplicate work in red
dfs(6)
├─dfs(5)coin 1
  ├─dfs(4)
  │  ├─dfs(3)
  │  │  └─dfs(2)... keeps branching
├─dfs(4) againsame state, recomputed
└─dfs(1) againalready solved inside dfs(4)

Every branch re-explores the same smaller amounts. With amount = 11 the duplication is already substantial; with amount = 10^4 it is catastrophic.

Approach 2: Memoized DFS (Implemented)

Intuition: The recursion has overlapping subproblems, so cache the answer for each remaining amount. The first call solves it; later calls are an O(1) lookup.

Time: O(amount · coins) Space: O(amount) cache + recursion
Solving dfs(6) with a cache: repeated states become hits
splitChange(6)
├─splitChange(5)coin 1 → computes 5, 4, 3, 2, 1, 0
│  └─splitChange(4)cached = 2
├─splitChange(4)coin 2 → cache hit, no recursion
└─splitChange(1)coin 5 → cache hit
splitChange(6) → 1 + dp[5] = 2 1 + dp[4] = 3 1 + dp[1] = 2 → min = 2

The cache stores Infinity too, so impossible amounts are also solved only once. Negative remainders return Infinity immediately and are never cached, since they are branch failures rather than states.

Approach 3: Bottom-Up DP (Tabulation)

Intuition: Fill the same table iteratively from 0 upward. Each dp[a] depends only on smaller amounts, so no recursion is needed.

Time: O(amount · coins) Space: O(amount)
Filling dp for coins [1, 2, 5], one amount at a time
dp[0] = 0 for a = 1 .. 11: dp[a] = min over coin <= a of dp[a - coin] + 1 a=1: dp[0]+1 = 1 -> 1 a=2: dp[1]+1 = 2, dp[0]+1 = 1 -> 1 a=3: dp[2]+1 = 2, dp[1]+1 = 2 -> 2 a=4: dp[3]+1 = 3, dp[2]+1 = 2 -> 2 a=5: dp[4]+1, dp[3]+1, dp[0]+1 -> 1 ... a=11: dp[10]+1 = 3, dp[9]+1 = 4, dp[6]+1 = 3 -> 3
dp[6] = 2 → + coin 5 → dp[11] = 3

No call stack, so amount = 10^4 is safe. The inner loop can iterate over coins or over amounts; both give O(amount · coins). Returning -1 is a final check on dp[amount] === Infinity.

Approach 4: BFS over Amounts

Intuition: Amounts are nodes; adding a coin is an edge of cost 1. The fewest coins is the shortest path from 0 to amount, so BFS by levels finds it.

A visited array prevents re-enqueuing amounts, so each of the amount + 1 states is expanded once. BFS can stop early, unlike bottom-up DP, but it stores a frontier queue.

A = amount, C = number of coin denominations, m = smallest coin.

Common Pitfalls

  • Greedy is wrong: coins = [1, 3, 4], amount = 6 → greedy uses 3 coins, optimal uses 2 (3 + 3).
  • Forgetting amount 0: the base case is 0, not -1 and not Infinity.
  • Returning Infinity: convert to -1 at the boundary.
  • Not caching unreachable amounts: caching Infinity is what prevents exponential recomputation of dead branches.
  • Wrong DP initialization: fill(Infinity), then dp[0] = 0. Filling with 0 makes every amount look reachable.
  • Index out of range: only read dp[a - coin] when coin <= a.
  • Recursion depth: top-down depth can reach amount / min(coin) (up to 10,000), which can overflow a default JS call stack. Prefer bottom-up for worst-case inputs.
