Path Sum

LeetCode 112 — Does a root-to-leaf path add up to the target?

Tree DFS BFS Recursion

Problem Overview

Given a binary tree and targetSum, return true if some path from the root down to a leaf sums exactly to the target. A leaf has no children; stopping at an internal node does not count.

Input: root = [5,4,8,11,null,13,4,7,2,null,null,null,1], targetSum = 22 Output: true // 5 + 4 + 11 + 2 = 22 Input: root = [1,2,3], targetSum = 5 Output: false // paths sum to 3 and 4 Input: root = [], targetSum = 0 Output: false // no path exists at all

Constraints: 0 <= nodes <= 5000, -1000 <= Node.val <= 1000, -1000 <= targetSum <= 1000.

Approach 1: Recursive DFS with a Running Sum Implemented

Intuition: carry the sum of the current path down the recursion. At a leaf, that running sum is a complete root-to-leaf sum, so compare it with the target. If either subtree succeeds, the tree succeeds.

Implemented in this repo Time: O(n) Space: O(h)
Example 1 — each node shows the running sum; only 5+4+11+2 reaches 22 at a leaf
5 → 4 → 11 → 7 → leaf sum 27 ≠ 22 → backtrack, try right: 5+4+11+2 = 22 ✓

Once the winning leaf is found, || short-circuits and the entire right subtree of 5 is skipped.

recurr(node, targetSum, counter): if node is null: return false newCount = counter + node.val if node is a leaf and newCount == targetSum: return true return recurr(node.left, targetSum, newCount) or recurr(node.right, targetSum, newCount)

Why the leaf test is essential

Counter-example: root = [1,2], targetSum = 1 — node 1 is not a leaf

Answer: false. Checking only newCount === targetSum would wrongly stop at the root.

Approach 2: Iterative DFS with an Explicit Stack

Intuition: recursion is a stack of pending branches. Store each node with the sum still needed below it; popping an entry resumes exactly the path the recursive call would have explored.

Time: O(n) Space: O(h)
Stack snapshots — entries are [node, remaining]
after pushing root
[5, 17]
pop 5, push children
[4, 13]
[8, 9]
pop 4, push 11
[11, 2]
[8, 9]
pop 11, push 7 and 2
[7, -5]
[2, 0]
[8, 9]
pop [7, -5]: leaf, remaining ≠ 0 → false → pop [2, 0]: leaf, remaining == 0 → true

[8, 9] is never popped. The stack holds at most one branch per level, so the space is O(h).

const stack = [[root, targetSum - root.val]]; while (stack.length) { const [node, remaining] = stack.pop(); if (!node.left && !node.right) { if (remaining === 0) return true; continue; } if (node.right) stack.push([node.right, remaining - node.right.val]); if (node.left) stack.push([node.left, remaining - node.left.val]); } return false;
When this wins: deep trees where the recursive version could overflow the call stack. Same O(h) memory, no recursion limit.

Approach 3: BFS with a Queue of (node, remaining)

Intuition: explore the tree level by level while carrying each path's remaining target. A leaf dequeued with remaining === 0 proves the answer. This reaches shallow leaves sooner, at the cost of holding a whole frontier.

Time: O(n) Space: O(w)
Queue evolution on Example 1
[[5, 17]] → [[4, 13], [8, 9]]
pop [4, 13] → [[8, 9], [11, 2]]
pop [8, 9] → [[11, 2], [13, -4], [4, 5]]
pop [11, 2] → [[13, -4], [4, 5], [7, -5], [2, 0]]
pop [13, -4]: leaf, ≠ 0 pop [4, 5] → push [1, 4] pop [7, -5]: leaf, ≠ 0 pop [2, 0]: leaf ✓

Notice remaining can go negative — with negative node values there is no safe early pruning.

const queue = [[root, targetSum - root.val]]; while (queue.length) { const [node, remaining] = queue.shift(); if (!node.left && !node.right && remaining === 0) return true; if (node.left) queue.push([node.left, remaining - node.left.val]); if (node.right) queue.push([node.right, remaining - node.right.val]); } return false;

Approach Comparison

Approach Time Space Pros Cons
Recursive DFS + running sum (implemented) O(n) O(h) Shortest code, path-local state, short-circuits Recursion depth can reach n
Iterative DFS + stack O(n) O(h) No stack-overflow risk, same memory footprint Manual push/pop bookkeeping
BFS + queue O(n) O(w) Reaches shallow leaves early Holds an entire frontier, usually more memory

n = nodes, h = height, w = maximum width.

Common Pitfalls & Key Insights

Testing the sum at internal nodes. In Example 1, 5 + 4 + 11 = 20, and in the counter-example the root alone equals the target. Only leaves end a path.
Treating null as an empty path. Returning true for a null node when the remaining target is 0 makes root = [], targetSum = 0 wrong.
Pruning when the sum exceeds the target. Node values can be negative, so a path can overshoot and come back. remaining legitimately goes negative in the trace above.
Sharing a mutable accumulator between siblings. Pass the updated sum by value; do not add and subtract from a single outer variable without backtracking it.
Key insight: a root-to-leaf path sum can be tracked either as "sum so far" (implemented) or "remaining target". They are equivalent: sum so far === targetSum iff remaining === 0 at a leaf.
Key insight: a one-child node is not a leaf. The condition is !left && !right, never !left || !right.
