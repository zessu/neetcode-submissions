Coin Change (Minimum Coins)

Fewest coins from an unlimited supply to reach an exact target sum

Dynamic Programming Memoization GeeksforGeeks · Medium

Problem Overview

Given coin denominations coins[] and a target sum, return the minimum number of coins that add up to exactly sum. Each denomination can be used any number of times. If the sum cannot be formed, return -1.

Input: coins = [9, 6, 5, 1], sum = 19 Output: 3 ( 9 + 9 + 1 ) Input: coins = [4, 6, 2], sum = 5 Output: -1 ( every coin is even )
Key idea: the answer for an amount depends only on the answers for smaller amounts. Cache those answers, or build them from 0 upward, and the exponential search collapses to O(sum × n).
dp[0] = 0   |   dp[x] = 1 + min(dp[x − coin]) for every coin ≤ x

Approach 1: Top-Down Memoization (submission-0)

Intuition: solve breakDown(19) by trying each coin as the next one used. The same remaining amount is reached through many different orderings, so cache the result the first time it is computed.

Without the cache, amounts such as 10, 9 and 5 are recomputed along every path. With it, each amount is solved once: O(sum) states × n coins.

Constraint risk: the recursion depth is O(sum). On Node 22/26, minCoins([1], 10000) throws RangeError: Maximum call stack size exceeded — the memoization does not prevent the stack from growing. The iterative version below removes this failure mode.

Selected relaxations: dp[10] = dp[1] + 1 = 2, dp[11] = dp[6] + 1 = 2 (6+5), dp[18] = dp[9] + 1 = 2 (9+9), and dp[19] = dp[10] + 1 = 3 (9+9+1).

  • Allocate dp of length sum + 1, filled with Infinity; set dp[0] = 0.
  • For each amount from 1 to sum, try every coin that fits.
  • Keep the minimum of dp[amount] and dp[amount - coin] + 1.
  • Return dp[sum], converting Infinity to -1.

Why Not Greedy?

Taking the largest coin first is only correct for canonical coin systems (like US currency). This problem allows arbitrary denominations.

coins = [9, 6, 5, 1], sum = 11 Greedy: 9 + 1 + 1 → 3 coins Optimal: 6 + 5 → 2 coins ✓
Greedy fails silently: for [4, 6, 2], sum = 5 it correctly reports impossible, but for [9, 6, 5, 1], sum = 11 it returns 3 instead of 2. A fast wrong answer is still wrong.

Approach Comparison

Approach Time Space Correct? Notes
Brute-force recursion O(n^sum) O(sum) Yes Recomputes overlapping subproblems
Memoized DFS (submission-0) O(sum × n) O(sum) Yes Stack overflow risk at sum = 10^4
Bottom-Up DP (submission-1) O(sum × n) O(sum) Yes Optimal; no recursion, no stack risk
BFS over amounts O(sum × n) O(sum) Yes Shortest path on an unweighted graph; needs queue + visited set
Greedy O(n log n) O(1) No Fails on non-canonical denominations

Common Pitfalls

  • Assuming greedy works. Sort + largest-first is not valid for arbitrary coins; use DP.
  • Forgetting the recursion limit. sum can be 10^4; memoization reduces time, not depth. Prefer tabulation.
  • Returning Infinity. Convert unreachable sums to -1 at the end.
  • Handling sum 0. The correct answer is 0; initialize dp[0] = 0.
  • Treating it as 0/1 knapsack. Coins are unlimited; reading the already-updated smaller amount enables reuse.
  • Using != Infinity. Prefer === Infinity or Number.isFinite for clarity.
